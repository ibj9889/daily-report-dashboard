# AI 요약 작성 기준

대시보드의 주간/월간 요약은 이 기준으로 작성한다. 요약을 새로 쓰거나 고칠 때(`/update-dashboard`) 항상 이 문서를 먼저 읽는다.

## 입력과 출력

- 원문: `private/dump/weeks/<월요일날짜>.txt`, `private/dump/months/<YYYY-MM>.txt`
  - `node scripts/build.mjs --dump` 를 실행하면 만들어진다.
  - 무엇을 써야 하는지는 `private/dump/todo.json` 에 있다.
- 인원 id: `private/members.json` 의 `id` 값 (예: 박인권 = `pik`)
- 출력: 기간마다 JSON 파일 하나를 `private/summary-parts/` 에 저장한다.
  - 주간: `week-<월요일날짜>.json` (예: `week-2026-08-31.json`)
  - 월간: `month-<YYYY-MM>.json` (예: `month-2026-09.json`)
  - 다음 빌드 때 `private/summaries.json` 으로 자동 병합된다.
- 파일은 UTF-8, JSON 문법을 지킨다. 저장 후 `node -e "JSON.parse(require('fs').readFileSync('파일','utf8'))"` 로 문법을 확인한다.

## 주간 요약 형식

```json
{
  "headline": "그 주를 한 문장으로. 50자 안팎",
  "overview": "사업부 전체 흐름을 3~5문장 단락으로",
  "byMember": [
    { "id": "pik", "text": "그 사람의 그 주 핵심 업무 1~3문장" }
  ],
  "issues": [
    { "text": "문제나 리스크 한 줄", "owner": "kds", "status": "진행중" }
  ],
  "directives": ["사업부장 지시, 회의에서 정해진 사항"],
  "upcoming": [
    { "date": "2026-09-21", "text": "SK DFS 군산 장비 출하" }
  ],
  "questions": ["다음 회의에서 확인하면 좋을 질문"]
}
```

- `byMember`: 그 주에 보고가 있었던 사람만 넣는다. 순서는 members.json 의 order 순.
- `issues`: 3~7개. 고객 클레임, 장비 이상, 일정 지연, 인력 부족처럼 회의에서 다룰 만한 것만 고른다. `status` 는 원문으로 판단되면 `진행중`, `해결`, `보류` 중 하나, 판단이 어려우면 생략한다. `owner` 는 담당 id, 모르면 생략.
- `directives`: 원문에 지시나 결정이 없으면 빈 배열.
- `upcoming`: 원문에 날짜가 적힌 앞으로의 일정만. 날짜를 지어내지 않는다. `date` 는 YYYY-MM-DD.
- `questions`: 2~5개. 진행 상황 확인, 담당 미정, 지연 원인처럼 사장님이 회의 때 바로 물어볼 수 있는 문장으로. 비난조는 피한다.

## 월간 요약 형식

```json
{
  "headline": "그 달을 한 문장으로",
  "overview": "4~6문장 단락",
  "highlights": ["완료, 수주, 출하처럼 그 달의 성과"],
  "issues": [{ "text": "...", "owner": "kds", "status": "진행중" }],
  "byMember": [{ "id": "pik", "text": "2~4문장" }],
  "directives": ["..."],
  "carryOver": ["다음 달로 넘어가는 과제나 일정"]
}
```

월간 요약은 해당 월 원문(`months/`)을 기준으로 쓰고, 이미 작성된 주간 요약(`private/summaries.json` 또는 `private/summary-parts/week-*.json`)을 참고해도 된다.

## 내용 원칙

1. 원문에 있는 사실만 쓴다. 추측, 평가, 칭찬을 덧붙이지 않는다.
2. 숫자, 날짜, 고객사명, 장비 사양은 원문 표기 그대로 옮긴다.
3. 사람 이름은 실명으로 쓴다(대화명 Rick, 젼태, 현수는 쓰지 않는다). 직책은 필요할 때만.
4. 인사, 개인 정보는 요약에 넣지 않는다. 채용 후보 이름, 연봉 조건, 건강, 입원, 경조사, 연차 사유 같은 내용은 빼거나 "채용 관련 협의"처럼 일반적으로만 쓴다.
5. 그 주에 실제로 일어난 일 중심으로 쓴다. 매일 반복되는 같은 문장은 한 번만 반영한다.

## 문체 원칙 (사람이 쓴 문서처럼)

1. 한국어로 쓴다. 영어 약어(UL, EOL, DAQ 등)는 원문대로 둔다.
2. **가운뎃점(U+00B7) 문자를 절대 쓰지 않는다.** 나열은 쉼표, 슬래시, "와/과", "및"을 섞어 쓴다.
3. 별표, 이모지, 장식용 화살표(→, ▶ 등)를 쓰지 않는다.
4. 모든 항목을 같은 틀("A - B", "~ 진행 중")로 찍어내지 않는다. 어떤 항목은 짧게, 어떤 항목은 두 문장으로 쓴다.
5. 번역투("~를 통해", "~에 대해", "~에 있어서", "~할 수 있을 것으로 보인다")를 피하고 "~로", "~에", "~하겠다"처럼 바로 쓴다.
6. "결론적으로", "주목할 만하다", "시사하는 바가 크다", "혁신적인" 같은 상투어를 쓰지 않는다.
7. 문장 끝은 "~했다", "~하다", "~예정이다"처럼 보고서체로 통일하되 길이와 리듬은 다양하게 한다.
